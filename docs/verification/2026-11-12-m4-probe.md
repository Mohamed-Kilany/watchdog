## Checklist — M4-T10

- [x] **Enumerate** every `CaptureRequest.Key` advertised by the camera
      (`availableCaptureRequestKeys`) and the matching result-key inventory
      (`availableCaptureResultKeys`); request and result keys are correlated by canonical
      `Key.getName()` because the two Camera2 types are distinct.
- [x] **Safe sequence**: each documented candidate value is applied with one
      `session.capture` on the live session; the request is rebuilt from the currently
      requested controls plus companion setup keys (for example `TONEMAP_MODE` before a
      preset curve). The app keeps streaming and never reconfigures the session for a probe.
- [x] **Outcome classification**: `accepted` (the result reflects the submitted value),
      `ignored` (submitted but the result does not reflect it) and `error` (the HAL rejected
      the request or no result arrived). Keys that need a new session or a one-shot trigger
      are reported as `skipped` with a reason; vendor keys without a documented probe table
      are `unprobed`.
- [x] **Abort guard**: five consecutive real capture failures abort the run; a rejected
      value records `error` for that value and probing continues. No matrix aborted.
- [x] **Host command**: `watchdog device probe [--serial] [--camera ID] [--key KEY] [--json]
      [--output FILE]` renders the Markdown compatibility matrix or raw JSON.
- [x] **Long-run keepalive**: the host pings every 5 s and caps poll slices at 1 s while a
      probe runs, so the app's 15 s heartbeat does not close the session. The full matrices
      took 21.6–23.9 s each, past the old failure point.
- [x] **Asynchronous camera switch**: `set_controls(camera_id)` acknowledges before the
      camera thread has opened the new device. The host now polls `STATE` until the target
      camera is reported and retries `probe_keys` while the app answers `CAMERA_NOT_READY`.
- [x] **Matrices committed** for every camera of the only available device:
      [camera 0](../device-matrices/sm-a515f-android-13.md),
      [camera 1](../device-matrices/sm-a515f-android-13-camera-1.md),
      [camera 2](../device-matrices/sm-a515f-android-13-camera-2.md),
      [camera 3](../device-matrices/sm-a515f-android-13-camera-3.md).

- Every camera reported the same two ignored values:
  `android.control.aeExposureCompensation` at `-20` and `+20`; the capture result kept the
  current compensation (`0`). The request was accepted by the HAL (no `error`), but a single
  capture does not let AE settle at the extremes. The interactive `set-control` path with its
  750 ms settle window was verified separately in M4-T04.
- The three skipped keys are identical on all cameras:
  `android.control.aePrecaptureTrigger` and `android.control.afTrigger` (one-shot 3A triggers
  would disturb the live stream) and `android.jpeg.gpsLocation` (metadata, not a camera
  capability).
- Camera 0 does not advertise 20 of the documented keys (manual colour correction, manual
  sensor, tonemap, edge/hot-pixel, distortion, rotate-and-crop, black-level lock and the
  statistics modes). Cameras 1–3 additionally omit `android.control.afRegions`, for 21
  unadvertised keys. These are listed at the bottom of each matrix.
- Single-key spot check: `device probe --camera 1 --key android.control.aeMode --json`
  returned one entry with two values, `0 → 0` and `1 → 1`, both `accepted` and reflected.
  This exercises the canonical `--key` filter and confirms the camera switch waited until the
  front camera was ready.
- The full per-value evidence (requested value, label, outcome, reflected flag, result value
  and elapsed milliseconds) is in the four matrix files.
