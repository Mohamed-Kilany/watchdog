## Checklist — M4-T13

- [x] **Panels never cover the video**: the preview is a centred 16:9 `SurfaceView`
      (letterboxed at 2400x1080) with a scrollable panel on each side; no overlay is drawn
      over the preview area.
- [x] **All current control states**: the panels are built from the same per-session state
      store as the host (`requested`/`actual`/`supported`/`source`), so every advertised
      control appears without app changes. Entries are grouped into **Connection**,
      **Exposure**, **Focus**, **White balance**, **Lens**, **Flash/scene**, **Output** and
      **Recording**; supported controls without a value show `—`.
- [x] **Live updating**: the status handler reposts every `STATUS_INTERVAL_MS = 500` ms;
      camera/stream fields and the control readouts refresh from `uiStatus()`.
- [x] **Readable at arm's length**: label/value rows use the panel typography from
      `res/values/styles.xml` (labels ~14 sp caps, values ~20 sp); verified at roughly
      60 cm from the 6.5" display in both palettes.
- [x] **High-contrast mode**: a persisted checkbox in the left panel switches the activity
      theme to `Theme.WatchdogRemote.HighContrast` (black panels, white values, yellow
      labels, cyan headings). `PanelContrast.kt` mirrors the normal palette and the JVM
      tests assert WCAG AA for normal text and AAA for large text in both palettes.
- [x] **Screenshot tests**: `PanelScreenshotTest` captures the normal and high-contrast
      panels and asserts the contrast pairs. The test source is compiled by the new CI step
      `compile instrumented tests (not run)`; it is not executed because the emulator job is
      manual-only by project decision.
- [x] **Theme recreation survives**: toggling high contrast calls `recreate()` and detaches
      and re-attaches the preview surface. Three toggle transitions were logged
      (12:36:56, 12:39:08, 12:44:45); every one logged
      `preview surface detached; reconfiguring capture session` followed by
      `camera STREAMING (was STREAMING)` and the preview recovered. No
      `unconfigured Input/Output Surface` rejection and no camera error after the fix.
- [x] **Manual latency check**: a 30 fps screen recording of a host `zoom_ratio` change
      shows the preview change between frames 62→63 and the panel `zoom_actual` readout
      between frames 71→72 — the panel updated ~300 ms after the preview took effect, inside
      the 500 ms refresh bound. Host command round-trip was 91 ms.
- [x] **Camera switch reflects promptly**: in a second recording, the panel camera id
      changed at video t≈2.13 s while the preview switched at t≈2.87 s; the panel reflects
      the requested camera immediately and the preview follows the session rebuild.
- [x] **No regressions**: the app stayed in `STREAMING` through both recordings, with
      `dropped_frames=0` in the sampled state snapshots and no queue-overflow or
      `CAMERA_IN_USE` entries.

### Latency measurement

Method: `adb shell screenrecord --time-limit 7 --bit-rate 4000000` at 30 fps, then the
video was decoded to 30 fps PNG frames offline (ffmpeg 7.1.1, analysis only). Mean absolute
luma difference was computed between consecutive frames in two fixed rectangles: the
preview (584,236)-(1776,907) and the panel zoom readout (1808,189)-(2186,243).

```
zoom_ratio 1.0 -> 2.0
  preview change:   frame 62 -> 63   t=2.07 -> 2.10 s   diff 65.23
  panel change:     frame 71 -> 72   t=2.37 -> 2.40 s   diff  2.42
  panel lag after preview: 9 frames = 300 ms (refresh bound 500 ms)
  host round_trip_ms: 91 ms

camera_id 0 -> 1
  panel change:     frame 64        t=2.13 s            diff 13.39
  preview change:   frame 86        t=2.87 s            diff 80.55
```
