      (`camera_id`, `stream_size`, `still_format`, `still_size`, `video_size`,
      `video_bitrate`, `video_codec`, `video_container`, `stream_rotation`, `jpeg_quality`,
      `audio`, `physical_camera_id`) and are intercepted by the app instead of being sent
      as Camera2 request keys.
- [x] **Defaults** on camera 0: 1280x720 live stream, JPEG still at the largest available
      size (4000x3000), 1920x1080 video, 8 Mbit/s, H.264, MP4, audio off, rotation 0,
      JPEG quality 80, `physical_camera_id=none`, `ae_fps_range=[30,30]`. The reported
      actuals match every default.

      sizes as `OUT_OF_RANGE`, and a rejected change leaves the previous actual untouched.

      whole structural batch rolls back — the valid sibling reports `ROLLED_BACK` and
      neither `stream_size` nor `jpeg_quality` changes. Accepted non-structural siblings in

- [x] **Clean restore**: all T09 controls return to defaults after the suite.
- [x] No transient `camera thread unavailable` replies and no retries in the whole run

## Failures found (do not hide)

| # | Severity | Description | Issue link | Workaround |
|---|---|---|---|---|
| 1 | high | The first T09 device run crashed the app during `stream_size` changes: `FramePipeline.stop()` closed the `ImageReader` from the camera thread while the pipeline thread could still be copying a frame, so `ByteBuffer.get()` threw `IllegalStateException: buffer is inaccessible` and killed the process. | PR #31 | fixed by closing the reader on the pipeline thread after in-flight frames and dropping frames from a reader closed mid-teardown; the final run passed the 3-round rebuild stress and 4000x3000 stream |
| 2 | low | The initial T09 harness expected a forced `[15,15]` FPS reconciliation after a size change. The A51 sustains 30 fps for every YUV size, so the product correctly keeps `[30,30]`; the harness now asserts FPS stability instead.
